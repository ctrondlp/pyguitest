# API reference

Every public name in `pyguitest`, with the capability each one needs.
Generated by `scripts/gen-api-docs.py` — edit the docstrings, not this page.

New to the library? [getting-started.md](getting-started.md) goes from an
empty file to a working script; this page is the lookup you want once you
know roughly what to reach for. [recipes.md](recipes.md) answers the
task-shaped questions — waiting properly, filling a form, screenshots, CI —
and [troubleshooting.md](troubleshooting.md) starts from the symptom when a
call finds nothing, types nothing or captures nothing.

**Reading the tables.** *Needs* is the `Capability` a call requires; ask
`gui.supports(...)` before depending on it, or let the call raise
`CapabilityUnsupported`. A blank means the call works on any session, and
"uses X if present" means the call adapts rather than fails when X is
missing. A few calls can also be marked **X11 only** — a capability nothing
but `X11Backend` provides. Nothing carries that mark today, because Windows
provides every tier-6 capability and macOS serves `pointer_position()`: the
capability model working, not an annotation gone missing. See
[wayland-audit.md](developers/wayland-audit.md) for why.

## Getting a session

Most scripts have the same shape — open a session, find the window, work
through named elements, and assert on what the application did:

```python
import pyguitest

gui = pyguitest.connect()
gui.require(pyguitest.Capability.ELEMENT_TREE, pyguitest.Capability.POINTER_BUTTON)

window = gui.wait_for_window("Preferences", timeout=10)
if not gui.focus_window(window):
    raise AssertionError("the window manager would not focus Preferences")

gui.text_field("Name").set_text("Ada")
gui.checkbox("Subscribe").click()
gui.button("Save").click()

gui.expect_text(name="Status", equals="Saved")
gui.close()
```

`connect()` picks the backends for the session it finds; name them yourself
only when you need a specific one. It does **not** raise when nothing can
drive this desktop -- automatic selection falls back to a `NullBackend` and
you still get a session, which then refuses each call individually. That is
why the second line is there: `require` is the check that fails early and
names what is missing, rather than letting a script run on into a refusal.
`focus_window` is checked for the same reason -- it returns False rather
than raising when a window manager declines, and typing into an unfocused
window sends the keystrokes somewhere else.

Two forks a first script meets. `Element.set_text` writes through the
accessibility interface and sends no key events, which is what you want when
the value is the point; `Session.type_text` sends real keystrokes, which is
what you want when the application's own key handling is under test. And
`expect_*` raises on failure for use directly in a test, where `wait_*`
returns a value for you to branch on.

Open an automation session.

`connect(backend: str \| Sequence[str] \| None = None, environment: Environment \| None = None, backend_options: dict \| None = None, **kwargs: Any) -> Session`

## Session control

A session is the handle on one desktop. `supports` and `require` are how a script asks what this desktop allows before depending on it, rather than discovering it from a traceback halfway through a run.

| Call | Needs | What it does |
|------|-------|--------------|
| `supports(capability: Capability)` |  | Whether this session provides `capability`. |
| `require(*capabilities: Capability)` |  | Raise unless every capability is available. |
| `capabilities` |  | Everything this session can do. |
| `report()` |  | A support table for this session, for logs and bug reports. |
| `close()` |  | Release the backend's resources. |

### `supports`

For branching on what a desktop can do -- taking a screenshot where
capture exists, skipping that assertion where it does not. Where the
test simply cannot run without it, prefer require(), which raises at
the top of the test naming the missing capability instead of letting
it surface mid-run.

A True answer means the capability is wired up, not that every call
through it will succeed: permission can still be refused, and a
consent prompt can still be dismissed. See `capabilities` for the
whole set and report() for a readable table.

### `require`

For declaring a test suite's needs up front rather than failing part
way through a run.

### `capabilities`

The backend's capabilities plus the tier-1 ones Session implements
directly -- process launch and timing work regardless of which backend
was selected, or whether one was found at all.

### `report`

Appends the backend's own provider breakdown when it offers one --
CompositeBackend.report() shows which member serves which
capability, which was otherwise unreachable from here even though
Session.report() is the CLI's whole `pyguitest` output.

### `close`

Closes display connections, virtual input devices and any portal or
libei session the backend opened. Prefer the context-manager form,
which closes on the way out even if the body raises:

    with pyguitest.connect() as gui:
        ...

What this does *not* do is undo input state: a key or button left
down by press_key/press_button stays down afterwards, because
nothing here tracks what a caller is holding. Release them yourself
-- see release_key. Applications started with start_app() are also
unaffected; use that as a context manager, or terminate them, to
avoid leaving windows behind.

## Elements

The recommended way to drive an application: match on what a widget is and what it is called, not where it happens to be.

| Call | Needs | What it does |
|------|-------|--------------|
| `button(name: str, within: Element \| None = None)` | `ELEMENT_TREE` | Return the push button labelled `name`. |
| `text_field(name: str, within: Element \| None = None)` | `ELEMENT_TREE` | Return the text box named `name`. |
| `dropdown(name: str, within: Element \| None = None)` | `ELEMENT_TREE` | Return the combo box named `name`. |
| `checkbox(name: str, within: Element \| None = None)` | `ELEMENT_TREE` | Return the check box named `name`. |
| `link(name: str, within: Element \| None = None)` | `ELEMENT_TREE` | Return the link named `name`. |
| `menu_item(name: str, within: Element \| None = None)` | `ELEMENT_TREE` | Return the menu item named `name`. |
| `element(role: str \| Sequence[str] \| None = None, name: str \| re.Pattern[str] \| None = None, within: Element \| None = None, enabled: bool \| None = None, visible: bool \| None = None, description: str \| re.Pattern[str] \| None = None, predicate: Callable[[Element], bool] \| None = None)` | `ELEMENT_TREE` | Return the first element matching every given filter. |
| `elements(role: str \| Sequence[str] \| None = None, name: str \| re.Pattern[str] \| None = None, within: Element \| None = None, enabled: bool \| None = None, visible: bool \| None = None, description: str \| re.Pattern[str] \| None = None, predicate: Callable[[Element], bool] \| None = None)` | `ELEMENT_TREE` | Return every accessible element matching every given filter. |
| `root_element()` | `ELEMENT_TREE` | The accessible-tree root. The replacement for the X11 window tree. |
| `window_element(title: str \| re.Pattern[str])` | `ELEMENT_TREE` — uses `WINDOW_LIST` if present | The accessible Element for the window matching `title`. |
| `focused()` | `ELEMENT_TREE` — uses `WINDOW_STATE` if present | The accessible element that currently has keyboard focus, or None. |
| `focus_tracking_works()` | `ELEMENT_TREE` — uses `WINDOW_STATE` if present | Whether this desktop actually publishes per-widget keyboard focus. |

### `button`

Push buttons only. A toolbar item, a tab, or a menu entry that looks
like a button to a user usually publishes a different role -- reach
for menu_item(), or element(role=...), rather than assuming this
covers them.

### `text_field`

Tries three roles in order -- ENTRY, TEXT, PASSWORD_TEXT -- because
no single one covers every toolkit's idea of a text box: at-spi2
versions without a dedicated single-line role report one as `text`,
and a password field is its own role everywhere.

A read-only field is still returned; it simply never reports typed
input (its READ_ONLY state is the honest signal to check first).

### `dropdown`

A Qt combo box publishes its *current text* as the accessible name
and discards the name set on it, so the stable name often travels in
the accessible *description* instead. Try the description before
giving up.

### `checkbox`

Check boxes only, not radio buttons or toggle buttons -- each is its
own role. Read the returned element's `checked` to see its state,
and `checkable` first: `checked` answers a real boolean on
everything, whether or not it has a box to check.

### `link`

The link's text is its name. A Chromium or Electron application
publishes no accessible tree at all until an assistive technology is
announced, so this raising ElementNotFound on every link in such an
app is a sign of that rather than of a wrong name -- see
docs/troubleshooting.md.

### `menu_item`

Finding a menu item does not require its menu to be open -- the
accessible tree publishes the whole structure -- so the usual way to
invoke one is to find it and `click()` it, with no need to click
through its parent menus first.

A submenu's own entry carries this role too, and a checkable item
reports its state through `checked`. Top-level menu bar entries
("File") may publish `menu` rather than `menu item` depending on the
toolkit; use element(role=...) where that distinction matters.

### `element`

Raises ElementNotFound if nothing matches. See elements() for what
each filter accepts.

### `elements`

`name`/`description` take a plain string (exact match) or a compiled
regex, matched with `.search()` -- the same convention find_window
uses for titles:

    gui.elements(role=Role.PUSH_BUTTON, enabled=True)
    gui.elements(name=re.compile(r"^Save"))

`predicate` is an escape hatch for anything the named filters do not
cover, such as an ancestor/descendant relationship:

    gui.elements(predicate=lambda e: some_label.is_ancestor_of(e))

`within` scopes the search to one element's subtree, and takes an
`Element` -- for a window, `gui.window_element(title)`, not the
`Window` from `find_window`.

`role` may name several roles at once --
`role=(Role.PUSH_BUTTON, Role.CHECK_BOX)` -- matching any of them.
Prefer this over one `elements()` call per role when driving a whole
page of mixed controls: every backend's role filter resolves through
one search of the subtree in scope, so N separate role searches walk
that same subtree N times over, where one search naming all N roles
walks it once. Confirmed live: on AT-SPI, walking a ~130-element
window role by role (16 calls) took over a minute; the same 16 roles
in one call took a few seconds, the walk's own cost either way.

### `root_element`

The desktop-wide root: its children are *applications*, whose
children are their windows. Rarely what a test wants directly --
elements()/element() search from here already, and
window_element(title) is the scoped starting point for one window.

Reach for it to enumerate what is running, or as a `within=` of
last resort. Walking the whole tree is expensive: an unscoped,
unfiltered walk crosses every application on the desktop.

### `window_element`

Scopes an element search to one window via `within=`:

    gui.element(role=Role.CHECK_BOX, name="Enable",
                within=gui.window_element("Preferences"))

`title` takes a plain string (matched literally, as a substring) or
a compiled regex (matched with `.search()`) -- see find_windows.
Distinct from find_window, which returns a Window -- the backend-
agnostic handle used for geometry and placement, not element search.
Raises WindowNotFound if nothing matches, matching find_window.

A same-named decoration proxy is preferred against by process, where
one can be identified. Found live on a real GNOME/Mutter desktop: an
X11 client with no client-side decoration gets a second, shell-owned
AT-SPI application (`mutter-x11-frames`) publishing its own `frame`
carrying the *exact same title* as the real window -- chrome and a
`Close` button, none of the application's own widgets. Name matching
alone cannot tell the two apart, and `mutter-x11-frames` enumerated
first, so this returned the decoration and every search scoped
`within=` it found nothing. `find_window`, which answers from the
window manager's own list rather than the accessible tree, does not
see that proxy at all -- it is not a real toplevel -- so its `pid` is
trustworthy where the name alone is not, and is used here to prefer
an exact match when one is available. Falls back to the first name
match if `find_window` cannot place the title (nothing wrong with a
backend that fills no `pid`, or a title `find_windows` does not carry
the same way an accessible name does) -- so a desktop with no such
proxy, or a backend with no window list at all, sees no change.

### `focused`

The active window's application is searched first and the whole
desktop only if that finds nothing, so the answer does not depend on
which application the tree happens to enumerate first. On a desktop
that does not publish per-widget focus this returns the shell's own
toplevel (or None) rather than a widget -- focus_tracking_works() is
the check for that, and is worth asking first.

See _focused_widget for why a widget is preferred over a toplevel
claiming the same state, and _focus_scope for why the search is
scoped before it is broadened.

### `focus_tracking_works`

AT-SPI's FOCUSED state is what focused(), assert_focused() and
assert_tab_order() read, and some desktops never set it on
individual widgets. Measured live on GNOME Shell 50.4 (Wayland):
the only element carrying it anywhere on the desktop was the
shell's own toplevel, across three separate toolkits (VTE, GTK4,
GTK3), whichever window was active -- so a focus assertion there
can never match a real widget, however the application behaves.
See docs/validation.md.

Deliberately not a Capability: those are static, per-backend facts,
and this one can only be answered by looking at the tree right now.
Ask before depending on the three methods above:

    if gui.focus_tracking_works():
        gui.assert_focused(name="Password")

A live probe of this moment, not a permanent verdict -- it is
False when nothing at all currently has focus, which on a healthy
desktop usually means an active window with nothing focused in it
rather than a desktop that cannot report focus.

## Pointer

Coordinates are absolute screen pixels, and `screen=` selects the monitor. Prefer driving a named element over clicking a point where you can: a coordinate goes stale the moment a window moves. `glide` and `move_mouse_naturally` exist for applications that only react to real movement, such as hover menus.

| Call | Needs | What it does |
|------|-------|--------------|
| `move_mouse(x: int, y: int, screen: int = 0)` | `POINTER_MOVE` | Move the pointer to an absolute position. |
| `glide(x: int, y: int, duration: float = 0.2, rate: float = 120.0, via: Sequence[tuple[int, int]] = (), start: tuple[int, int] \| None = None, ease: Callable[[float], float] \| None = None, screen: int = 0)` | `POINTER_MOVE` — uses `POINTER_QUERY` if present | Move the pointer to (x, y) as a stream of events, not a jump. |
| `move_mouse_naturally(x: int, y: int, duration: float \| None = None, pace: float = 700.0, rate: float = 120.0, via: Sequence[tuple[int, int]] = (), start: tuple[int, int] \| None = None, screen: int = 0, arc: float = 0.15, wobble: float = 1.0, overshoot: float = 0.04, latency: float \| None = None, pause: float = 0.0, seed: int \| None = None)` | `POINTER_MOVE` — uses `POINTER_QUERY` if present | Move the pointer the way a hand does, not the way a line does. |
| `click(button: int = 1)` | `POINTER_BUTTON` | Press and release a mouse button. Replaces ClickMouseButton. |
| `press_button(button: int)` | `POINTER_BUTTON` | Press a mouse button. 1 is left, 2 middle, 3 right. |
| `release_button(button: int)` | `POINTER_BUTTON` | Release a mouse button. |
| `drag(start: tuple[int, int], end: tuple[int, int], button: int = 1, duration: float = 0.3, rate: float = 120.0, via: Sequence[tuple[int, int]] = (), ease: Callable[[float], float] \| None = None, settle: float = 0.05, screen: int = 0)` | `POINTER_BUTTON`, `POINTER_MOVE` — uses `POINTER_QUERY` if present | Press at `start`, glide to `end`, release. Drag-and-drop. |
| `scroll(dx: int = 0, dy: int = 0)` | `POINTER_SCROLL` | Scroll by whole wheel detents: `dy` positive is up, `dx` right. |

### `move_mouse`

One event: the pointer is where it was, then it is here, with
nothing in between. See glide() for the animated form.

### `glide`

move_mouse() teleports, which is enough to click with and wrong for
everything that watches the pointer on its way: drag-and-drop only
arms once motion crosses a threshold with a button down, hover
reveals and tooltips need enter/leave crossings, kinetic scrolling
and gesture recognisers read velocity off event timestamps, and hot
corners fire on approach rather than arrival.

The route is straight unless `via` names waypoints, and the useful
non-straight path is a deliberate one -- crossing a particular widget
on the way, holding the angle a GTK submenu's navigation triangle
wants -- not the randomised, natural-looking wobble that bot-detection
evasion goes in for. That would only buy flakiness here, and nothing
on this side of the compositor is looking for it. Waypoints are
passed through rather than landed on exactly, since points are spaced
by distance along the whole route.

move_mouse_naturally() is the deliberate exception to that: a shaped
path for a region that reacts to being crossed and for a take that has
to look performed, seeded so it still replays exactly.

`duration` is wall-clock seconds and `rate` the points per second, so
the two give `duration * rate` events; the default 120 Hz is in the
range of a real mouse without flooding a backend that pays per event.
`ease` reshapes progress -- a callable from a fraction in [0, 1] to
one, clamped -- and is off by default because constant velocity is
what a flick test wants; an ease-out decelerates into the target and
a flick released at zero speed does not throw.

The origin is `start`, or wherever this session last put the pointer.

### `move_mouse_naturally`

glide() is shaped like a machine on purpose -- straight legs, constant
velocity unless an `ease` says otherwise, and no wobble at all, its
own docstring calling the natural-looking alternative something that
"would only buy flakiness here". This method is the deliberate
exception, for the two cases where that reasoning does not hold:

* **A region that reacts to the pointer being over it.** Reveal-on-
  hover, tooltips, enter/leave crossings and hot corners all fire on
  the *path*, so how the pointer arrives is part of what is under
  test rather than noise in it.
* **A take that has to look like a person did it** -- a desktop action
  recorded for film, TV or a live demo, where a straight line at
  constant speed reads as a script however good the click is.

What "like a hand" means here is four things, each a published
behaviour rather than a taste:

* a **speed ramp** -- minimum-jerk, accelerating out of the start and
  decelerating into the target (see _natural_profile);
* an **arch** -- every leg bows perpendicular to itself, `arc` as a
  fraction of that leg's length, so the path curves where a straight
  line would corner;
* a **drift** -- `wobble` pixels of slow seeded sway across the path;
* an **overshoot and correction** -- `overshoot` as a fraction of the
  last leg, which is the most recognisable part of a fast aim.

`via` are waypoints, as in glide(), with one difference: this lands on
each of them, where glide passes through at whatever distance-spacing
gives. An arch needs both of its ends known, so the bow is built per
leg and each leg finishes exactly on its endpoint. The final target is
exact for the same reason glide's is -- everything clicked afterwards
depends on it -- and `overshoot` reaches it by aiming the last leg
past it and correcting back, never by arriving and then leaving.

`duration` is wall-clock seconds; left as None it comes from the
distance and `pace` in pixels per second, clamped rather than scaling
linearly into absurdity on a long move. `rate` is events per second.
`latency` is the pause before the pointer starts moving, defaulting to
the session's own `event_delay` so one knob paces the whole script,
and `pause` inserts a single hesitation part-way through, which is
what breaks a long aim into two movements. `event_delay` is still
charged once at the end, as glide does, because _walk must not charge
it per point.

`seed` makes the whole path reproducible -- identical events for a
repeated take, and a test that cannot flake. Left as None it is
derived from the move itself (_path_seed), so the same move always
comes out the same while different moves differ. This is where a
natural-motion implementation has to be careful: unseeded randomness
would reintroduce exactly the flakiness glide() refuses, and make a
second take impossible to match.

### `click`

Clicks wherever the pointer already is -- this moves nothing. Pair
it with move_mouse(), or use click_element(), which takes its
destination from the element's own extents:

    gui.move_mouse(x, y)
    gui.click()

    gui.click_element(gui.button("Save"))   # move and click

`button` is 1 left, 2 middle, 3 right. Do not reach for 4/5 to
scroll: X11's button-as-wheel encoding is not how the other
backends express a wheel at all -- scroll() is, in detents, on every
backend (see its docstring for the sign convention).

`event_delay` is applied after the press *and* after the release, so
a session configured with one holds the button down for that long
rather than emitting a zero-length click some toolkits drop.

### `press_button`

Presses wherever the pointer already is -- this moves nothing --
and holds the button down until release_button(). For a plain click
use click(); for a press-move-release use drag(), which handles the
intermediate motion a toolkit needs to see a drag as a drag.

### `release_button`

A press with no matching release outlives the session: nothing here
tracks held buttons to let go of them on close, and the compositor
goes on believing the button is down -- which looks to the user like
a stuck drag they cannot click out of. Pair every press_button with
this, under try/finally if anything between them can raise, or use
click()/drag(), which pair them for you.

### `drag`

Press-teleport-release is not a drag in either GTK or Qt: both arm on
the press and start the operation only when motion afterwards passes
a threshold, so with no motion between them the sequence is a click
at the destination. The glide in the middle is what makes it a drag,
which is why this is a method and not three lines in a docstring.

`settle` pauses around the button events. The press has to reach the
source widget before motion arrives or there is nothing to drag, and
a release in the same compositor frame as the last motion is read by
some drop targets as a click on the target instead of a drop onto it.

A glide that raises does not leave the button held: the release is
still attempted, best-effort, and the glide's own error is the one
that propagates. A button left virtually down outlives the script --
every pointer move the *user* then makes is a drag, with nothing on
screen to say why -- which is the same stuck-state hazard
release_button documents, except here no caller wrote the press, so
no caller would think to pair it.

Every other argument is glide()'s, and means the same thing there.

### `scroll`

One unit is one notch of a physical wheel, not a pixel, and the
direction is X11's rather than Wayland's -- the same on every
backend, which took a fix on two of them. `GUIBackend.scroll`
has the reasoning.

## Keyboard

`type_text` is for literal text and `send_keys` for chords and named keys. Both go to whatever holds focus, so focus a window or element first -- see `focus_window` -- or the keystrokes land somewhere else. Typed text depends on the session keymap; [input.md](input.md) covers when that matters.

| Call | Needs | What it does |
|------|-------|--------------|
| `type_text(text: str, delay: float \| None = None, **kwargs: Any)` | `TEXT_ENTRY` | Type `text`, using the session's `key_delay` unless overridden. |
| `send_keys(keys: str)` | `KEY_EVENT` | Send literal text and key combinations in one string. |
| `press_key(key: str)` | `KEY_EVENT` | Press a key by name, without releasing it. |
| `release_key(key: str)` | `KEY_EVENT` | Release a key by name. |
| `tap_key(key: str)` | `KEY_EVENT` | Press and release a key. Replaces PressReleaseKey. |
| `press_tab(reverse: bool = False)` | `KEY_EVENT` | Press Tab (or Shift+Tab if `reverse`), advancing keyboard focus. |

### `type_text`

The keymap-aware path, and the right one for arbitrary or non-ASCII
text: it asks the backend to produce the characters rather than
naming keys to press, so it does not depend on the active layout the
way press_key does. `delay` is the pause *between characters*, and
defaults to the session's `key_delay` (itself 0.0 unless set at
connect time) -- raise it for a toolkit that drops fast input, such
as a field that re-validates or autocompletes on every keystroke.

This types into whatever has keyboard focus; it does not focus
anything. Focus the field first (`Element.focus()`, a click, or
press_tab), and on a multi-window app confirm the right window has
focus -- "the right app is frontmost" is not the same as "keys land
there". For literal text mixed with key combinations in one string,
see send_keys; for text containing its `^%+#&{}~` metacharacters,
see quote_for_type.

`**kwargs` reach the backend: `allow_keymap_unsafe=False` refuses to
type through a scancode-injecting backend (uinput, ydotool) that
cannot know the active layout, rather than typing the wrong
characters -- see GUIBackend.type_text.

### `send_keys`

Replaces X11::GUITest's SendKeys and its `{}` grammar -- see
quote_for_type for the escaping half of this contract. Special
characters:

    ^ % + # &   modifiers: Ctrl, Alt, Shift, Meta, AltGr
    ~ or \n     Enter
    ( )         group the following keys under a modifier
    { }         escape a special character, name a key by
                abbreviation, repeat one, or pause

Everything else is sent as literal text. A modifier not immediately
followed by `(` is pressed and released on its own, combined with
nothing:

    gui.send_keys("Hello, how are you?\n")
    gui.send_keys("%(f)q")        # Alt-f, then plain q
    gui.send_keys("^(+(l))")      # Ctrl-Shift-l
    gui.send_keys("+(abc)")       # Shift held: ABC
    gui.send_keys("{BAC}")        # Backspace
    gui.send_keys("{F1 F2 F3}")   # F1, F2, F3
    gui.send_keys("{TAB 3}")      # Tab, three times
    gui.send_keys("{PAUSE 500}")  # sleep 500ms

Key names inside `{}` are looked up case-insensitively in the active
backend's KEY_ALIASES, or else passed to press_key as written, so an
unabbreviated name works too: `{BackSpace}` in place of `{bac}`.

This is the classic ASCII grammar, faithfully ported -- not a
keymap-aware text-entry path. Use type_text for arbitrary or
non-ASCII text; this raises ValueError for a character with no
static key mapping (see GUIBackend.resolve_char_key), for malformed
`{}` syntax, and for a `{}` key name this backend does not resolve.

### `press_key`

`key` is passed to the backend as written, in that backend's own
key vocabulary: X11 keysym names (`"Return"`, `"Escape"`,
`"Control_L"`, `"a"`) on X11 and the xdotool/wdotool/wtype adapters,
evdev names on uinput. The abbreviations in GUIBackend.KEY_ALIASES
(`{BAC}`, `{PGU}`) are send_keys's `{}` grammar, not this -- nothing
is resolved here, so a name this backend does not know surfaces as
the backend's own error.

The name is a key, not a character to type: press_key("A") is the A
*key*, not a capital A (that is Shift held plus `"a"`, or simply
type_text).

Use this only to *hold* a key -- a modifier while something else is
pressed. For a single keystroke use tap_key, and for a combination
prefer send_keys("^(c)"), which releases in the right order even if
something between the press and the release raises.

### `release_key`

Same stuck-state hazard as release_button, and worse in practice: a
modifier left down survives this session and silently rewrites every
keystroke the *user* then types, with nothing on screen to say why.
Nothing here tracks held keys to release them on close. Pair every
press_key with this under try/finally, or let send_keys do the
pairing.

### `tap_key`

The normal way to send one keystroke. Takes the same backend-native
key names as press_key, and like it sends a *key*, not a character
-- for text use type_text, and for a key with modifiers use
send_keys:

    gui.tap_key("Return")
    gui.send_keys("^(s)")       # Ctrl-S, modifier released for you

### `press_tab`

Sugar over send_keys -- needs real key injection
(Capability.KEY_EVENT), unlike focused()/Element.focus(), which
only read or set AT-SPI state directly and need no injection
permission.

## Windows

A `Window` stays usable as a handle, but its `title`, `app_id` and `pid` are read when it is created and do not update themselves -- call `refresh_window` for current values rather than comparing against a title the application has since changed. Finding one by title is the usual way in, and a window the list already carries may still not be placed on screen: check `is_window_viewable` before acting on a position.

| Call | Needs | What it does |
|------|-------|--------------|
| `windows()` | `WINDOW_LIST` | Return every open window. |
| `find_window(title: str \| re.Pattern[str] \| None = None, app_id: str \| Sequence[str] \| None = None)` | `WINDOW_LIST` | The topmost window matching `title` and/or `app_id`. |
| `find_windows(title: str \| re.Pattern[str] \| None = None, app_id: str \| Sequence[str] \| None = None)` | `WINDOW_LIST` | Every window matching `title` and/or `app_id` (exact). |
| `active_window()` | `WINDOW_STATE` | The currently focused window, or None if nothing holds focus. |
| `window_at(x: int, y: int, screen: int = 0)` | `WINDOW_AT_POINT` | The topmost window covering a screen coordinate, or None. |
| `geometry(window: Window)` | `WINDOW_GEOMETRY` | `window`'s (x, y, width, height) in screen coordinates. |
| `move_window(window: Window, x: int, y: int)` | `WINDOW_PLACEMENT` | Move a window's top-left corner to (x, y). |
| `resize_window(window: Window, width: int, height: int)` | `WINDOW_RESIZE` | Resize a window to `width` by `height`. |
| `activate_window(window: Window)` | `WINDOW_ACTIVATE` | Raise and focus. There is no raise-without-focus operation. |
| `minimize_window(window: Window, minimized: bool = True)` | `WINDOW_MINIMIZE` | Minimize a window, or restore it when `minimized` is False. |
| `is_window_open(window: Window)` | `WINDOW_LIST` | Whether `window` is still in the window list. |
| `is_window_viewable(window: Window)` | `WINDOW_STATE` | Whether `window` is currently mapped and showing. |
| `refresh_window(window: Window)` | `WINDOW_LIST` | `window` as it is *now*, or None if it has closed. |
| `window_events(timeout: float \| None = None)` | `WINDOW_EVENTS` | Yield WindowEvents as the compositor reports them. |

### `windows`

**Ordered bottom-to-top**, so the last entry is the topmost window
and `windows()[-1]` is the one a user would say is in front. That
convention is what find_window() and window_at() both resolve ties
with; a caller doing its own filtering should take `[-1]`, not
`[0]`. On X11 the order is `_NET_CLIENT_LIST_STACKING`'s.

"Every window" is the window manager's own list, which is not the
same as what the user can see: it includes windows parked
off-screen, and a desktop's own panels and utility toplevels --
confirmed live on Xfce, where xfce4-panel alone holds several
same-titled toplevels, some of them off-screen. Filter with
find_windows()/find_window(), and ask is_window_viewable() where
"actually mapped and showing" is what matters.

Titles are not identifiers and can drift after a window opens (see
Window's docstring); `app_id` is the stable one where a backend
fills it in.

### `find_window`

Raises WindowNotFound if nothing matches, so a script stops where the
mistake is. See find_windows for how `title`/`app_id` combine and
what `title` accepts.

Same "last of windows() wins" convention window_at() uses for hit-
testing, not the first: windows() is ordered bottom-to-top by
_NET_CLIENT_LIST_STACKING, and more than one window can legitimately
share a title (confirmed live on Xfce -- xfce4-panel alone can hold
several same-titled toplevels, including ones parked off-screen).
Taking the first used to hand back whichever happened to sit at the
bottom of that list, which was reliably the wrong, invisible one.

### `find_windows`

At least one of `title`/`app_id` is required. Given both, a window
must satisfy each. `title` takes a plain string (matched literally,
as a substring -- see _title_pattern) or a compiled regex (matched
with `.search()`), the same convention `elements`/`element` use for
`name`/`description` -- over an identifier that can drift after a
window opens (see Window's docstring). `app_id` is an exact match
against one that should not drift, and may be several ids where the
same window is named differently by each protocol (`app_id=("a",
"b")`) -- the one case a single id cannot cover: see _app_id_match. It
is empty on backends that never fill it (see Window.app_id), and
nothing matches `app_id=""` on purpose, since that is "unset", not a
real identifier; an empty sequence matches nothing for that reason.

### `active_window`

What the *window manager* considers focused, which is not a promise
about where injected keystrokes will land. The two can disagree:
confirmed live on macOS, where a panel belonging to another process
(Quick Note's) took every keystroke while this kept correctly
reporting the application's own window, because that panel changed
no window-manager focus. So treat a matching answer here as
necessary, not sufficient -- if input is vanishing, check what is
really under the cursor with window_at()/element_at() rather than
trusting this.

None is an ordinary answer, not an error: an empty desktop, or a
moment between one window losing focus and the next gaining it. Use
wait_window_focus() to wait for a specific window instead of polling
this.

### `window_at`

The authoritative answer to "what will a click here actually hit",
and worth asking before a coordinate click rather than after. A
control's reported rectangle can lie outside its own window --
scrolled below the fold, say -- and clicking its centre then hits
whatever else owns that point: confirmed live on macOS, where a
widget's centre landed on the Dock, launched an unrelated
application and handed it the keyboard focus for the rest of the
run. element_at() is the finer-grained form of the same check.

Resolves ties the way windows() is ordered: topmost wins. None
means no window covers the point -- bare desktop, or off every
output.

### `geometry`

The most commonly missing capability (Capability.WINDOW_GEOMETRY),
and raises CapabilityUnsupported where it is absent rather than
guessing. Wayland gives a client no window coordinates of its own,
so there it depends on a compositor-specific route being available
(gnomeshell, kdotool, cosmic) -- `supports(Capability.
WINDOW_GEOMETRY)` is the way to ask, and `pyguitest doctor` says
what is missing.

`x, y` is the top-left corner. Whether decorations are included
varies by window manager, so compare geometries read in one session
rather than hard-coding pixel expectations, and re-read after any
move, resize or layout change instead of caching a snapshot.

One known caveat worth reading before building on this: on GNOME's
XWayland specifically, a geometry read straight after move_window()
can report a position nowhere near where the window actually
renders -- see docs/troubleshooting.md and validation.md. Do not
write a test that sets a position and reads it back.

### `move_window`

A request, not a command: a window manager may clamp it to keep the
window on an output, offset it by the decoration frame, or refuse a
maximized or fullscreen window outright. Nothing here waits for or
verifies the result.

Do not assert by reading geometry() back -- on GNOME's XWayland
that read can report a position nowhere near where the window
actually renders, even though the move visibly worked. See
docs/troubleshooting.md.

### `resize_window`

Also a request: a client's own minimum and maximum size hints win,
and a tiling window manager may ignore it completely. Whether the
size covers the decoration frame or just the client area varies by
window manager, so size a window relative to a geometry() read in
the same session rather than to a hard-coded number.

Resizing reflows the application's layout, so every element extent
read before this is stale -- re-read them afterwards.

### `activate_window`

The two are one operation on purpose: no desktop this supports
offers a reliable raise that leaves focus alone, so splitting them
would mean promising something a backend cannot keep.

Asks once and returns immediately -- it does not wait for the
request to be honored. A window manager may take a moment (or
refuse outright, under a focus-stealing-prevention policy), so a
script that clicks or types straight afterwards cannot tell whether
focus arrived. Follow it with wait_window_focus() whenever the next
step is input.

"Raise" can mean less than it sounds like: on macOS, raising a
window only reorders it *within* its own application, and the
application itself has to be activated for keystrokes to reach it
at all -- this does both there. On an application with several
windows, raising one does not raise its siblings.

### `minimize_window`

A minimized window stays in windows() -- it still exists, so
find_window() keeps matching it. is_window_viewable() is what
distinguishes the two states.

Minimizing usually unmaps the window, which can make its elements
stop publishing extents (or publish empty ones) until it is
restored; restoring does not re-raise or re-focus it, so follow
with activate_window() where the next step is input.

### `is_window_open`

Asked of the list rather than of the handle, because a handle does
not know it has died: reading geometry from a closed window raises
from somewhere inside the backend -- "no window with id 106" is a
real example -- rather than reporting cleanly that it is gone.

### `is_window_viewable`

The honest test for "is this on screen", as against merely present
in windows() -- which also lists off-screen and utility toplevels.
A one-shot state read, deliberately not a wait: wait_for_window()
and wait_window_close() are the polling forms.

"Showing" is about map state, not visibility to a human: a window
fully covered by another still answers True.

### `refresh_window`

A `Window` is a snapshot: its title was true when it was taken, and
the handle beneath it may since have gone. Both bite in practice --
an editor renames itself as soon as it has content, and a handle
held across a few seconds of work can address nothing at all -- so
anything that keeps one across time should exchange it for a fresh
one before using it, rather than assume.

Returns a *different* object with the same identity, so
`refresh_window(w) == w` while `refresh_window(w).title` may not
match `w.title`. None means it is gone, which is the answer callers
most often need and cannot get from the handle itself.

### `window_events`

Needs Capability.WINDOW_EVENTS. wait_for_window and
wait_window_close are what most callers want instead: they consume
this where it exists and poll where it does not.

## Screen and capture

Capture is the one area where desktops differ most in what they permit; `screenshot` reports rather than guesses when a session will not serve it. `capture_on_failure` is the one to reach for in a test suite, and `locate` finds a known image on screen when nothing publishes an accessible element.

| Call | Needs | What it does |
|------|-------|--------------|
| `screens()` | `SCREEN_INFO` | Every output, in advertised order. |
| `screenshot(path: str \| None = None, window: Window \| None = None, region: tuple[int, int, int, int] \| None = None)` | `SCREEN_CAPTURE` | Write a screenshot and return the path it was written to. |
| `capture_on_failure(directory: str \| None = None, name: str \| None = None, window: Window \| None = None)` |  | Capture a failure bundle if the wrapped block raises. |
| `locate(haystack: str, template: str, region: Sequence[float] \| None = None, metric: str = RMSE, threshold: float \| None = None)` | `IMAGE_LOCATE` | Find `template` within the already-captured image `haystack`. |
| `locate_image(template_path: str, within: Window \| None = None, threshold: float \| None = None, metric: str = RMSE)` | `IMAGE_LOCATE`, `SCREEN_CAPTURE`, `WINDOW_GEOMETRY` — uses `SCREEN_INFO` if present | Find `template_path` on screen, restricted to `within` if given. |

### `screens`

"Advertised order" is the display server's own, which is not a
statement about which output the desktop calls primary -- there is
no primary flag here, so a multi-monitor test should identify an
output by `name` rather than trusting index 0. The `screen=`
argument on move_mouse()/window_at() indexes this list.

A `Screen` reports size, scale and name but *not* its position in
the desktop's coordinate space, so this alone cannot say where one
output sits relative to another. `width`/`height` are physical
pixels, the same units geometry() and screenshot() use; `scale` is
DPI over 96 and never a pixel count.

### `screenshot`

With no arguments, captures the whole desktop to a temporary file.
`window` captures one window; `region` captures an `(x, y, width,
height)` rectangle in screen coordinates. The two are mutually
exclusive -- a region is already screen-absolute, so pairing it with
a window could only mean one of two different things.

How a window is captured depends on what the session offers, and
the difference is visible in the image. A backend declaring
Capability.WINDOW_CAPTURE (X11, GNOME Shell, Windows and macOS
today) reads the window's own pixels, so anything stacked on top of
it is absent, and a window hanging off the edge of the desktop comes
back whole. Everywhere else the window's rectangle is looked up
through WINDOW_GEOMETRY and cut out of a full-screen shot, which does
include whatever is covering it and does clip what is offscreen. Both
are honest screenshots of a window; only one is a screenshot of *just*
that window.

### `capture_on_failure`

A GUI test that fails tells you an assertion did not hold; a
screenshot, the accessible tree, the active window, and whatever had
keyboard focus at that moment usually tell you the whole diagnosis.
Capturing it after the fact is too late -- by then the app has been
torn down -- so it has to happen while the exception is still
propagating:

    with gui.capture_on_failure("artifacts"):
        gui.click_button("Save")
        assert gui.element(name="Saved")

Each artifact is attached to the exception under its own name --
`screenshot`, `accessibility_tree`, `active_window`,
`focused_element` -- as a file path, or `None` if it could not be
captured. The exception is re-raised untouched either way, so a test
runner reports the original failure and the files are there to look
at. Nothing is captured on success.

Each artifact is attempted independently, and a failing one never
replaces the failure it was trying to document, nor blocks the
others: a desktop with no AT-SPI still gets a screenshot; a session
with no capture backend still gets the tree. Whatever goes wrong for
one artifact is recorded on the exception as `<name>_error` and
swallowed -- the original exception is what the caller needs to see.

`directory` defaults to $PYGUITEST_SCREENSHOT_DIR, then the
system temporary directory. `window` narrows the screenshot the same
way it does for :meth:`screenshot`; the other artifacts are never
window-scoped.

### `locate`

Returns None if no match clears `threshold`. Unlike locate_image,
this searches a file rather than the live screen, and answers with
None rather than raising -- no display connection is involved.

### `locate_image`

Captures the whole desktop and, with `within`, restricts the search
to that window's rectangle, looked up via WINDOW_GEOMETRY. Either way
the match's (x, y, width, height) comes back in screen coordinates --
callers never add a window's offset back on. That takes two
corrections the image itself does not carry: where the capture
starts, which on Windows is the virtual desktop's corner (negative
where a monitor sits left of or above the primary); and its scale,
which on a Retina display is two device pixels per point. The origin
comes from `GUIBackend.desktop_region`, and the scale from the
captured image's own size against that rectangle. A backend with no
answer keeps image pixel (0, 0) as screen (0, 0) at one pixel per
unit, which is right on any single-monitor, non-HiDPI desktop.

The whole desktop is captured even for `within`, rather than only the
window's rectangle: a capture tool handed a rectangle hanging off the
screen may refuse it or quietly return less, and a smaller image than
asked for would read as a different scale. Searching costs the same
either way, since the search is cropped to the window first.

Raises ImageNotFound if no match clears `threshold`. With no
`threshold`, the single best match is always returned, however poor.

The search compares colour: alpha is not part of a match, so a
template's transparency -- or the alpha channel a capture carries,
which every macOS one does -- cannot turn an identical template into a
miss.

Worth knowing what a search costs, since that is what makes `within`
worth passing. Matching runs at 20-40us per pixel of haystack on an
ImageMagick build with no FFT delegate, which is the slow path and
the one a Windows install gives you: a full-screen search takes the
better part of a minute on a 1080p desktop and several on a 4K one.
The same search inside one window is usually a second or two, and it
cannot match the same control in a different window.

## Clipboard

Text only, and the selection a desktop calls the clipboard rather than the X11 primary selection.

| Call | Needs | What it does |
|------|-------|--------------|
| `get_clipboard(primary: bool = False)` | `CLIPBOARD` | The current text content of the clipboard, or of PRIMARY. |
| `set_clipboard(text: str, primary: bool = False)` | `CLIPBOARD` | Replace the text content of the clipboard, or of PRIMARY. |

### `get_clipboard`

`primary=True` reads the X11/Wayland PRIMARY selection instead --
what a middle-click paste inserts, and independent of the
clipboard proper: writing one never touches the other.

### `set_clipboard`

Replaces rather than appends, and the two selections are
independent: writing the clipboard never touches PRIMARY or the
other way round. See `get_clipboard` on `primary=`.

Text only -- there is no API here for images or other flavours, and
setting text clears whatever richer content the selection held.

On X11 a selection is owned by a live process rather than stored by
the server, so what happens after the owner exits is the desktop's
business: with no clipboard manager running, a selection written by
a process that then exits can simply vanish. Read it back with
assert_clipboard() where the test depends on it.

## Processes

`start_app` launches and hands back an `Application` to wait on and tear down, and is what a GUI test wants. `run_app` **blocks until the program exits** -- it is `subprocess.run` underneath, so pointing it at an application hangs the script until someone closes the window. Launching the application under test from the script is what makes a run repeatable.

| Call | Needs | What it does |
|------|-------|--------------|
| `start_app(command: str \| Sequence[str], **kwargs: Any)` |  | Launch a program without waiting. Replaces StartApp. |
| `run_app(command: str \| Sequence[str], **kwargs: Any)` |  | Run a program to completion. Replaces RunApp. |

### `start_app`

Returns an `Application`: a `subprocess.Popen` plus the lifecycle
the bare one leaves to the caller. Use it as a context manager when
the program should not outlive the block, which is almost always --
it terminates, and kills if that does not take:

    with gui.start_app([EDITOR, path]) as app:
        window = gui.wait_for_window("Editor", timeout=10)
        ...

Everything a `Popen` answered still works (`pid`, `wait`,
`terminate`, `poll`, `returncode`, ...), so code written before this
returned an `Application` needs no change; `app.process` is the
`Popen` itself.

A string `command` runs through the shell, matching StartApp; a
list does not. Prefer the list form for anything built from a
variable -- `start_app(["editor", path])` treats `path` as one
argument no matter what is in it, where the string form would let
a space or a `;` in it become shell syntax.

`**kwargs` go to `subprocess.Popen`. Note `env=` *replaces* the
environment rather than adding to it, which on a GUI session drops
DISPLAY/WAYLAND_DISPLAY and the app never appears -- pass a merged
copy to override one variable:

    gui.start_app(["app"], env={**os.environ, "LANG": "de_DE.UTF-8"})

### `run_app`

Same shell and `env=` behaviour as :meth:`start_app`: a string runs
through the shell, and `env=` replaces rather than extends the
environment. `**kwargs` go to `subprocess.run`.

## Waiting

Every `wait_*` call polls on an interval unless the backend can do better: a window wait is answered by real notification — `SetWinEventHook` on Windows, a compositor event stream on GNOME Shell, KWin, sway or niri — but only when it matches a `title`. On macOS, which has no event feed here yet, on every X11 session, and on any wait that names `app_id`, that same call polls every `interval` seconds instead. `timeout` bounds the wait in seconds, and `timeout` left `None` — which every `wait_*` here defaults to, `sync` excepted — waits indefinitely; there is no session-level default to fall back on.

| Call | Needs | What it does |
|------|-------|--------------|
| `wait(seconds: float)` |  | Sleep for `seconds`. Replaces WaitSeconds. |
| `sync(timeout: float = 1.0)` | `INPUT_SYNC` | Block until the compositor has consumed the input sent so far. |
| `wait_until(predicate: Callable[[], bool], timeout: float \| None = None, interval: float = 0.5)` |  | Block until predicate() is truthy, or timeout elapses. |
| `wait_for_element(role: str \| None = None, name: str \| None = None, within: Element \| None = None, timeout: float \| None = None, interval: float = 0.5)` | `ELEMENT_TREE` | Block until an element matching role/name appears. |
| `wait_until_gone(role: str \| None = None, name: str \| None = None, within: Element \| None = None, timeout: float \| None = None, interval: float = 0.5)` | `ELEMENT_TREE` | Block until no element matches role/name/within, or timeout. |
| `wait_for_window(title: str \| re.Pattern[str] \| None = None, timeout: float \| None = None, interval: float = 0.5, app_id: str \| Sequence[str] \| None = None)` | `WINDOW_LIST` — uses `WINDOW_EVENTS` if present | Block until a window matching `title` and/or `app_id`. |
| `wait_window_close(window: Window, timeout: float \| None = None, interval: float = 0.5)` | `WINDOW_LIST` — uses `WINDOW_EVENTS` if present | Block until `window` (from find_window or wait_for_window) closes. |
| `wait_for_process(name: str \| re.Pattern[str], timeout: float \| None = None, interval: float = 0.5)` |  | Block until a process matching `name` is running, or timeout. |
| `wait_for_idle(pid: int, timeout: float \| None = None, interval: float = 0.2, samples: int = 3, cpu_threshold: float = 0.01)` |  | Block until `pid` looks CPU-idle, or timeout. |
| `wait_for_file(path: str, timeout: float \| None = None, interval: float = 0.5)` |  | Block until `path` exists, or timeout. Returns whether it appeared. |

### `wait`

An unconditional sleep, and almost always the wrong tool: it is
simultaneously too short on a loaded machine and wasted time on a
fast one, which is how a suite ends up both flaky and slow. Wait for
the thing you actually mean instead -- wait_for_window,
wait_window_close, wait_window_focus, wait_for_process, wait_until,
or sync() where the backend can prove the compositor has consumed
the input.

Kept because a few situations have nothing to poll: an animation
with no observable end state, or a deliberate pause between
keystrokes (for which `key_delay` and `event_delay` are the
session-wide form).

### `sync`

The honest replacement for `wait()` after injection. Where a
backend offers Capability.INPUT_SYNC (libei today, via its
ping/pong round trip), this returns once the compositor has
actually taken the events rather than once a guessed interval has
elapsed::

    gui.click()
    gui.sync()
    assert gui.element(name="Saved")

It proves the compositor consumed them, never that the
application processed or repainted them -- `wait_until` on the
element state you care about is what answers that. This removes
one source of flakiness underneath it, not all of them.

Returns True once confirmed and False on timeout, matching the
rest of the wait family; raises CapabilityUnsupported where no
backend can round trip, since a silent no-op here would hand back
exactly the false confidence it exists to remove.

### `wait_until`

The general-purpose polling primitive behind element state waits --
"wait until this button is enabled" is
`gui.wait_until(lambda: button.enabled)` rather than a hand-rolled
sleep loop. Returns whether predicate() became truthy before
timeout; never raises on timeout, matching
wait_for_window/wait_window_close.

### `wait_for_element`

Poll-based only -- unlike wait_for_window, no backend currently
offers element-level change events, so there is no event-driven
branch here. Returns the first matching Element, or None on timeout
-- not ElementNotFound, since polling for something that may simply
not exist yet is the expected outcome, the same reasoning
wait_for_window uses.

### `wait_until_gone`

Mirrors wait_window_close for elements -- waiting for a "Saving..."
toast or a modal's spinner to disappear. Returns True once the
element is gone, False if timeout elapses first while it is still
present.

### `wait_for_window`

See find_windows for how `title`/`app_id` combine and what `title`
accepts; at least one is required.

Delegates to the backend's own event-driven implementation where
Capability.WINDOW_EVENTS is available and only `title` was asked for
-- real notification, not polling. Those backends are `win32`, on
Windows, and GNOME Shell, KWin, sway and niri on their desktops;
macOS is not one of them, its AXObserver being a later phase, and
neither is any X11 session. Everywhere else -- both of those, and any
call that names `app_id`, one id or several, because the event-driven
backends only ever learned to match a title -- this polls
find_windows every `interval` seconds instead, so a script does not
need to know which case it is in, or hand-roll the poll loop itself:
checking for WINDOW_EVENTS and falling back to a fixed sleep was
exactly the mistake examples/04_drive_an_editor.py made before this
existed.

`timeout` bounds the wait in seconds; None waits indefinitely.
Returns the matched Window, or None if `timeout` elapses first --
not WindowNotFound, since polling for something that may simply not
exist *yet* is the expected outcome here, unlike find_window.

A match is a window the window list carries, which under a reparenting
window manager is not yet a window that is *there*: measured on Marco,
this returns while `is_window_viewable` is still False and `geometry`
still reads the pre-placement position, and a move issued in that gap
is lost to the manager's own placement. Wait for
`is_window_viewable(window)` before acting on a window whose position
matters.

### `wait_window_close`

Replaces X11::GUITest's WaitWindowClose. Compares by `window.handle`,
which is stable for the backend that produced it (see the Window
docstring), rather than by title -- two windows can share a title,
and a title can change before the window actually closes.

Uses the same event-driven-where-possible, poll-otherwise split as
wait_for_window: with Capability.WINDOW_EVENTS, watches for a "close"
event naming this window; otherwise polls windows() every `interval`
seconds for its disappearance. `timeout` bounds the wait in seconds;
None waits indefinitely. Returns True once closed, False if `timeout`
elapses first while it is still open.

### `wait_for_process`

`name` is `.search()`ed against the full command line, the same way
Session.find_window matches window titles. Returns the matched
process's pid, or None on timeout.

Reads /proc where it is available and `ps axo pid= -o args= -ww`
otherwise, so this works on FreeBSD (no /proc unless linprocfs is
mounted) and inside a container that hides it. Raises
PyGUITestError if neither route works, rather than reporting an
empty process table -- which would look exactly like "your process
is not running".

**On Windows the match is against the executable's filename alone** --
`"notepad.exe"`, never `"C:\...\notepad.exe /A file.txt"`. Windows
keeps no command line anywhere `CreateToolhelp32Snapshot` can reach,
and the one API that has it (WMI) costs a subprocess of around a
second on every poll. So a pattern naming the program works
(`wait_for_process("notepad")`), and a pattern that depends on an
argument matches nothing and times out rather than raising -- most
often a script behind its interpreter, where `"manage.py"` finds
nothing and `"python"` finds every Python on the machine.

Nothing else about pids is narrower on Windows, and two routes avoid
matching a name at all: `start_app(...).pid` where this session started
the program, and `Window.pid` -- which `win32` fills in from
`GetWindowThreadProcessId` -- where it did not. Both feed
`wait_for_idle` directly, and the second identifies the process behind
the window actually being driven rather than the first one sharing its
name.

### `wait_for_idle`

"Idle" means its CPU usage stayed under `cpu_threshold` (a fraction
of one core) across `samples` consecutive polls -- CPU-idle, not
"the UI stopped changing"; no backend here has an event stream to
watch for the latter (see docs/developers/wayland-audit.md for what
Wayland actually exposes). Useful after e.g. clicking "Export" and waiting
for the exporting process to stop working before checking its
output. A pid that has already exited counts as idle immediately --
but a pid whose CPU time cannot be *read* raises rather than
counting as idle, which is the distinction this used to get wrong:
with /proc unreadable it reported a process pinned at 100% as idle,
so a test that should have failed passed instead.

Where there is no readable /proc -- FreeBSD without linprocfs, or a
container with hidepid=2 -- CPU time comes from `ps`, whose
resolution varies (whole seconds on procps, centiseconds on
FreeBSD). If it is coarser than `interval` -- so coarse that a
process using a whole core would still read as idle -- this raises
rather than answering badly. On Windows, CPU time comes from
`GetProcessTimes` instead, at a resolution neither of those platforms
can match.

Note the resolution also sets a floor under `cpu_threshold`: the
smallest load that can be distinguished is resolution/interval of a
core, which with /proc's 0.01s tick and the default 0.2s interval is
5%, not the 1% the default threshold names. Loads under that floor
read as idle. Raise `interval` to lower it.

### `wait_for_file`

For a process under test writing output somewhere -- an export, a
log file -- rather than polling os.path.exists in a hand-rolled loop.

reads as a test failure rather than the unsupported-desktop

Reads through `get_clipboard`, so `primary=True` checks PRIMARY

### `assert_accessible`

### `assert_no_missing_accessible_names`

### `assert_no_duplicate_accessible_names`

Two buttons both called "Delete" are ambiguous to a screen reader
and to `gui.button("Delete")` alike -- whichever the locator returns
first is a coin toss, and a test written against it fails the day
the order changes.

Compared per role rather than globally: a "Save" button beside a
"Save" menu item is ordinary, and flagging it would be noise.

### `click_element`

Where the element publishes no accessible action to name -- a widget
whose provider offers neither Invoke nor Toggle nor an MSAA default
action, measured live on a `SysListView32` cell in
pyguitest-recorder -- `element.click()` calls this instead of raising,
because a coordinate click is what a person does with such a widget and
what the refusal used to advise. The element is still the locator: its
rectangle is read fresh each call rather than baked in ahead of time,
and only the gesture falls back to the pointer.

The spelling for an element with no session behind it -- one taken
straight from a backend, where `element.click()` has nothing to
delegate to. Either reads the same to a caller; this one is also what
`element.click()` ends up calling.

Needs Capability.ELEMENT_GEOMETRY, plus the pointer capabilities --
which come from whichever input backend the session was built with
(`win32`, `macquartz`, X11/XTEST, the portal), not from the
accessibility one. Raises PyGUITestError where extents() has no
rectangle for this element -- it is not showing, or the backend reports
none -- the same split `double_click_element` makes. `element.click()`
raises ElementNotActionable for that case instead, so that the typed
refusal a caller already catches keeps its meaning.

### `double_click`

Whether a pair of clicks *is* a double-click is the toolkit's
judgement, not this package's: GTK and Qt each measure the gap
between the two presses against a threshold that defaults to 400ms
and is settable per desktop.

So the four events go out back-to-back, deliberately skipping the
`event_delay` pause that calling click() twice would take between
them. At an `event_delay` of 0.2s that pause alone puts 400ms
between the presses and delivers two single clicks -- a test that
then passes against a widget that never saw a double-click, which
is the failure this package works hardest to avoid. A double-click
is one user action, so it takes one `event_delay` at the end, the
same as every other action here.

### `double_click_element`

The spelling for an element with no session behind it -- one taken
straight from a backend, where `element.double_click()` has nothing
to delegate to. Either reads the same to a caller; this one is also
what `element.double_click()` ends up calling.

Two `element.click()` calls are not a double click: each is a
separate round trip over the accessibility bus, which is slower
than any toolkit's double-click interval, so the pair arrives as
two single clicks and a double-clicked folder icon simply does not
open.

The element is still the locator -- its rectangle is read fresh
each call, rather than baked in ahead of time -- and only the
gesture falls back to the pointer, because that is where this
package's real double_click lives. Needs Capability.ELEMENT_GEOMETRY.

Raises PyGUITestError if extents() has no rectangle for this element
-- it is not showing, or the backend reports none -- rather than
ElementNotActionable, which means something more specific: no click
or press action for element.click() to fall back to.

### `element_at`

What window_at is for windows, with no `screen` argument: the
accessible tree is addressed in one desktop-wide coordinate space.

The answer is only as good as the extents behind it. A toolkit that
misreports them -- GTK4 has been seen placing every widget at the
origin -- makes one element claim every point, and nothing here can
tell that apart from a correct answer, so a caller turning a
coordinate into a locator should check that the element it got back
really covers the point (extents() says).

### `expect_checked`

Two waits, not one: `expect_element` first, which raises
`ElementNotFound` if the control never appears, then the state is
re-read until the deadline. So "no such control" and "the wrong
state" are different exceptions, and the worst case is twice
`timeout` rather than once.

A control whose toolkit publishes no checked state at all reports
`Element.checked` as None, which equals neither True nor False -- so
this times out and then says "but it is unchecked", because None is
falsey. Read `Element.checkable` first on a widget you do not know.

### `expect_element`

The raising sibling wait_for_element deliberately lacks, for the
same reason expect_window exists next to wait_for_window: a script
written against a specific recorded element treats its absence as
the failure, not a branch to handle.

### `expect_showing`

Two waits, as in `expect_checked`: `expect_element` raises
`ElementNotFound` where the control never appears, and only then is
`Element.visible` re-read until the deadline, raising
`AssertionError`. The worst case is twice `timeout`.

`Element.visible` means something slightly different on each
platform, and on Windows and macOS it answers True rather than admit
it could not tell -- its own docstring has the three definitions and
says which backend is lenient. So a pass here is weaker evidence on
those two than it looks; where it matters, the stronger check is that
the action the element exists for actually worked.

### `expect_text`

Re-read until `timeout` rather than checked once: a check made
right after the action it verifies would otherwise race the
application, which has not necessarily finished redrawing by the
time the click returns.

`timeout` is spent twice over in the worst case -- once waiting for
the element to exist, where its absence raises `ElementNotFound`,
and again waiting for the text to match, where a mismatch raises
`AssertionError` naming both sides.

### `expect_window`

The raising sibling wait_for_window deliberately lacks (see its
docstring): a script that already knows the window it wants exist is
an error, not a branch to handle, is the common case a generated
replay is written against. See wait_for_window for how `title`/
`app_id` combine and what `title` accepts.

A lookup and nothing else. It does not raise, focus, resize or
otherwise disturb the window it hands back -- focus_window() is for
that, and is deliberately a separate call: an earlier version of
this method activated every window it found, which is fine for an
application window and actively destructive for a desktop or a
menu. Binding the desktop while an application menu was open raised
the desktop, dismissed the menu, and left the clicks that followed
landing on nothing -- found live on MATE.

### `extents`

None where the element occupies no screen space -- it publishes no
rectangle, or reports an empty one because it is not showing.

The counterpart of geometry() for elements, and separate from it
because the two are answered by different backends: a window
rectangle can come from the compositor, an element's only ever from
the accessible tree. Needs Capability.ELEMENT_GEOMETRY.

### `focus_window`

Three things activate_window() on its own does not do: it waits for
the window's geometry to stop changing first (a still-animating
window can be clicked at a position it is about to leave), it asks
more than once (a window manager can drop a single request outright,
focus-stealing prevention being the usual reason), and it checks
whether the request was honored rather than assuming. Seen live as
typed text landing in the terminal a replay script was itself
running in, because the window it had just found did not hold focus
yet at that instant.

Returns whether `window` ended up focused. Never raises on its own:
a backend without WINDOW_GEOMETRY, WINDOW_ACTIVATE or WINDOW_STATE
simply reports False, since not being able to ask is not a different
answer from "it did not take".

A True here is as good as `active_window()`, which is the thing it
checks -- and on macOS that is necessary but not sufficient for
keystrokes to arrive: a panel belonging to another process can take
them while changing no window-manager focus, so this still reports
True. See `active_window()` for the measured case and for what to
check instead when input is vanishing.

`attempts` bounds the retry, and the two ways an attempt can fail are
treated differently. A `CapabilityUnsupported` means asking is
impossible, so it reports False at once rather than paying for
`attempts` identical refusals. Anything else is this attempt failing
-- a dropped request, a window-manager call that hung into a
`BackendCallTimeout` -- and the next attempt is made, which is what
the parameter is for.

### `is_button_pressed`

Same numbering as click() -- 1 left, 2 middle, 3 right -- and
reports the *desktop's* state, so a button a user is physically
holding reads as pressed too, not only one this session injected.
See the note above for the Wayland and XWayland caveats.

### `is_key_pressed`

Takes the same backend-native key name as press_key. Useful for
asserting a modifier was actually released after a combination; see
the note above, and be aware key state under XWayland is accurate
only while an X client holds focus.

### `is_window_cursor`

Replaces IsWindowCursor. Impossible on Wayland, where cursor shape is
negotiated privately between client and compositor.

### `lower_window`

Sends a window to the bottom of the stack. There is no Wayland
route: the foreign-toplevel protocols expose activate and close but
nothing to lower, so this raises CapabilityUnsupported there rather
than approximating it by raising everything else.

Not a mirror of activate_window(), which deliberately couples
raising with focusing: this only restacks, and what happens to
keyboard focus afterwards is the window manager's policy. Read
active_window() if the next step depends on it.

### `pointer_position`

In the coordinate space `screens()` reports. Works on X11, Windows
and macOS; see the note above for why an XWayland answer can be
silently stale. To check where a click will land, prefer
window_at()/element_at() over comparing this against an expectation.

### `require_version`

The counterpart of require() for the package itself rather than the
desktop: a script written against this release declares that fact up
front and fails here, naming both versions, rather than mid-run with
an AttributeError on an API an older release does not have.

Delegates to the module-level pyguitest.require_version(), which
also works before connect(); this method exists so a script holding
only `gui` declares its floor the same way it declares the
capabilities it needs.

### `row_values`

For a control that nests each row's cells beneath it as children --
confirmed live against a UIA `ListView` (WinDirStat's real
extension-summary list, each `list item` holding one `text` child
per column). Reads each child's `name`, which is where both backends
put a cell's displayed value.

A GTK `GtkTreeView` never nests this way, whatever its column count:
it publishes no row element at all. Measured live on
pyguitest-recorder's probe window -- a one-column `Gtk.TreeView`
(`First row`/`Second row`/`Third row`, and the `Folders` tree, whose
rows are `Documents`/`Reports`/`Q1`/`Q2`/`Notes`/`Trash`) -- every
one of those names is a `table cell` directly inside the table,
`table row` matches nothing at all, and this method on one of those
cells answers `()`. Measured again on a three-column
`Gtk.ListStore`: three `table column header` children (`Name`,
`Count`, `Color`) followed by the six `table cell`s flat, in
row-major order. Nothing groups those into rows but the caller
already knowing the column count, so this method does not cover that
shape -- reading it means chunking
`elements(role=Role.TABLE_CELL, within=table)` by the count
`elements(role=Role.TABLE_COLUMN_HEADER, within=table)` gives, by
hand, since nothing here has that structure to read automatically.

### `set_window_title`

Renames *another* application's window, which X11 permits any client
to do -- that is the impersonation note, and the reason no Wayland
protocol offers it. Mostly useful for tagging a window a test
created so later lookups are unambiguous.

The application may well rename it back: a title is the client's to
set, and anything that redraws it (a document change, a tab switch)
overwrites this. Do not use it as durable identity -- `app_id` is
the stable handle where a backend fills it in.

### `tree_items`

`elements(within=root)` only ever sees what the accessibility tree
already has *visible* -- a collapsed tree row's children are not
there to find until something opens it, the same way they are not
there on screen. This walks `root`, expanding every branch it finds
still collapsed (`expandable` and not `expanded`) before descending
into it, so a caller gets every row the user could reach by clicking
every disclosure triangle in order, not only the ones already open
when this was called.

`root` is the *container* the rows live in -- the tree, list or table
element itself, not a row inside it. Where the next section says a
toolkit publishes revealed rows beside their branch, that is the
whole reason: a row passed here is not a container of anything, so a
collapsed one answers nothing.

Where a revealed row goes
-------------------------
Opening a branch does not put its rows in the same place on every
toolkit, and `child.children` alone cannot tell the two apart:

- **UI Automation nests them.** The branch's own `children` grows, so
  reading it after `expand()` finds them. Measured on WinDirStat's
  real tree, where a `tree item` holds the rows it revealed.
- **AT-SPI on GTK flattens them.** The opened row keeps *no*
  children at all, and the rows it revealed are published as new
  siblings of it, in the container's own child list. Measured live on
  a GTK3 `GtkTreeView` (the probe window's `Folders` tree): with
  `Documents` collapsed, `Documents.children` was `[]`, and after
  `Documents.expand()` it was still `[]` -- while the tree's own
  children went from `[column header 'Folder', 'Documents', 'Trash']`
  to `['Folder', 'Documents', 'Reports', 'Notes', 'Trash']`. The
  revealed rows appear in pre-order beside the row that revealed
  them, exactly as the flattened list on screen reads. A walk that
  only recursed into `child.children` therefore found every row that
  was already open and never one it had just opened itself.

So a container's children are re-read after each expansion, and the
walk resumes from where it stopped rather than from the snapshot it
started with. That picks up rows revealed beside their branch (GTK)
and leaves the nested case (UIA) exactly as it was, since there the
list does not change and the recursion into the branch finds them
instead. The one thing this assumes about order is that a toolkit
publishes revealed rows at or after the position of the row that
revealed them, which is what pre-order flattening means and what both
measured toolkits do; one that inserted them *before* their branch
would leave them unseen. The result is not deduped either, because
there is nothing to dedupe on: a live backend hands out a fresh
wrapper per read, so two reads of one row are two objects that merely
look alike, and a container publishing the same row twice yields it
twice rather than once.

Only the reads matter here, and one is added where it counts: a
container is re-read once per expansion, never once per child, so a
tree with nothing left collapsed costs exactly the walk it did before.

`role` filters what is *returned* -- `Role.TABLE_CELL` for a GTK tree
view's rows, `Role.TREE_ITEM` for UI Automation's, say -- without
changing what gets walked or expanded; `None` (the default) returns
every descendant, matching `elements()`'s own convention. Rows this
expands stay expanded afterward: collapsing them back would cost a
second full walk for a state nothing asked to have preserved, the
same tradeoff `os.walk` makes about a directory's mtimes.

`max_depth` bounds how deep the *containers* nest, the same bound
`element_at` polices descent with on both backends and for the same
reason: a cyclic or malformed tree must not spin forever. A real tree
exhausts its actual depth long before 24 matters; a caller automating
something deeper can raise it. On a flattening toolkit it bounds less
than it looks like it does, since every row sits one level below the
tree itself however deep the branch it came from -- it is not a limit
on rows. A cycle is still caught: an element listing itself among its
own children is only walked again where an expansion actually added
something to walk, and `expand()` no-ops on a row already open.

Needs Capability.ELEMENT_TREE to walk children at all, and
Capability.ELEMENT_ACTION only where a branch actually has to be
opened -- a tree with nothing left collapsed runs on the first alone,
and the second is asked for before the first expansion rather than on
the way in.

### `wait_for_pointer_activation`

Not a query, and deliberately not spelled `pointer_position()`:
Capability.INPUT_CAPTURE (the `inputcapture` backend, opt-in --
`connect(backend="inputcapture")`) can only ever answer this at the
moment the compositor itself decides to divert input here, which
happens when the user's actual pointer physically moves across one
of the screen's edges. There is no way to trigger that on demand,
so this can legitimately block for as long as `timeout` allows
waiting for someone to do that -- and once it happens, **every
physical or logical pointer/keyboard/touch device the compositor
chose to divert stops reaching the desktop at all** until this
method has read the answer and released it, which it does as its
very next step. Call this only when that trade is genuinely wanted,
never as a drop-in replacement for a synchronous position read.

Returns the pointer's position in the coordinate space `Screen`
reports, or None if `timeout` elapsed with nobody crossing an edge
-- the ordinary outcome, matching every other `wait_for_*` method
here, not an error. `timeout=None` waits indefinitely.

### `wait_window_focus`

A window can exist -- wait_for_window has already returned it -- for
a moment before the window manager actually gives it focus, e.g. a
freshly-opened window still animating into place. Nothing else here
polls for that: activate_window() asks for focus once and returns
immediately, so a script that clicks or types right after it cannot
tell whether the request was honored yet, only that it was made.
Seen live: typed text landing in the terminal a replay script was
itself running in, because the window it had just clicked into did
not hold focus yet at that instant.

Returns whether `window` held focus by the deadline -- False is a
real answer to check, not something to guess from a None.

#### `actions`

The names `do_action` takes. Treat it as a set, not a sequence: it
comes back sorted on Linux and Windows but in AX's own preference
order on macOS, so indexing into it means something different per
platform. Print it before reaching for a toolkit-specific action
name -- what a widget publishes is the toolkit's choice, and an
element that publishes none at all is why `click` has a pointer rung.

#### `alive`

Every property above assumes this and raises from wherever it is
touched otherwise -- an application redraw, a closed dialog, a row
destroyed by a list that has scrolled past it. Checking first turns
that crash into a clean answer, the same shape `Session.
is_window_open` already gives for a stale `Window` handle: an
`Element` held across time should be asked this before it is used,
rather than assumed good.

What this cannot tell you: whether the reference has gone stale in
the other direction, addressing a *different* live widget that
happened to reuse the same identity. Nothing in this interface
promises identity survives a redraw at all -- there is no
`refresh_element`, unlike `Window`, because nothing here remembers
the locator that found it in the first place to search again with.

#### `checkable`

Read this before trusting `checked`, which has no state to report on
an element that has none -- and answers `None` where the platform
says so rather than inventing a False. How it is decided is the
platform's business -- a Toggle pattern on Windows, an at-spi state,
the role plus a menu item's mark character on macOS -- but the
question it answers is the same one everywhere.

#### `checked`

`None` is a real answer, not a failure, and the annotation means it:
on Windows an element with no Toggle pattern and no radio-selection
state has nothing to be checked, and an *indeterminate* control --
a mixed-state check box -- has not said "set" or "not set" either.
Read `checkable` first to know whether the value means anything,
and treat `None` as "it did not say" rather than as False.

#### `child`

`find`'s first match, with the same recursive reach, and None rather
than an exception where nothing matches -- the opposite convention
from `Session.element`, which raises. Useful for a local lookup
inside an element already in hand.

#### `children`

One level only: `find` and `child` are the recursive pair. The order
is whatever the toolkit publishes rather than anything sorted here,
so position within this list is a locator of last resort -- it breaks
the first time someone inserts a widget.

#### `choose`

Through the control's own accessibility interface, which is why it
keeps working when the list is long enough to scroll. The mechanics
differ underneath: Windows and macOS open the popup first, because a
combo box's items often do not exist in the tree until it is open,
and then look for the item inside the control and beside the whole
window in turn -- the two kinds of combo box put it in different
places. When the text does not match, `options()` is what to print.

#### `click`

The toolkit's own action first, named -- Invoke, Toggle, an MSAA
default action, AT-SPI's `click`. Where the element publishes none at
all, the click falls back to the pointer at the element's own
rectangle, which is what a person does with a widget that offers
nothing; `click_by_pointer` is that step on Windows and macOS, and on
Linux it is dogtail's own coordinate click, already the last item in
the ladder there.

An element with no session behind it -- one taken straight from a
backend -- has no pointer to reach, and raises `ElementNotActionable`
rather than doing nothing; `Session.click_element` is the same call
spelled for that case.

`via` chooses the route. `"action"` is the accessible action only,
raising `ElementNotActionable` where there is none; `"pointer"` is
the user pathway only (extents, move, click), raising rather than
silently substituting the action; `"auto"` (the default) is today's
ladder. `None` means "use the session's `click_via`".

#### `collapse`

A no-op where `expanded` already reads False, for the reason `expand`
gives. On Windows and macOS an element with nothing to collapse
raises `CapabilityUnsupported` rather than doing nothing silently.

#### `description`

Always a string, empty where there is none. Where a control publishes
no `name`, this is usually where its label went, which makes it the
second thing to try in a locator. On macOS it falls back to the same
attribute `name` does, so the two can come back identical there.

#### `do_action`

The names are the ones `actions` publishes. Windows and macOS also
accept at-spi's spellings, so `click`, `press` and `activate` all
mean the native invoke there and a script written against Linux keeps
working. Both raise `ValueError` listing what the element does offer
when the name is unknown, and `ElementNotActionable` when it is a
real action this element does not publish -- which is what tells a
typo apart from a widget that cannot. On Linux the name is passed to
the toolkit as given, so the refusal is the toolkit's own.

#### `double_click`

Not an accessible action, the way click is. `click` names an action
the toolkit publishes and lets the toolkit perform it; a
double-click is a gesture on the pointer, and no toolkit publishes
one on the bus -- two `click()` calls are two round trips, slower
than any toolkit's double-click interval, so the pair arrives as two
single clicks. So the element stays the locator and the gesture
falls back to the pointer, which needs the pointer capabilities on
top of Capability.ELEMENT_GEOMETRY.

An element a Session handed out answers this. One taken straight
from a backend has no session to reach the pointer through, and says
so rather than doing nothing; Session.double_click_element is the
same call spelled for that case.

`via` may only be `"pointer"` (or `None`/`"auto"`, both of which mean
pointer here): no toolkit publishes a double-click action, so
`"action"` is an honest refusal instead of the silent pointer click
that happens today.

#### `enabled`

True where the toolkit will not say, on all three backends -- the same
leniency `visible` documents. Worth waiting on rather than asserting
once: a Save button is disabled until the document is modified, which
is `Session.wait_until(lambda: save.enabled)`, not a single read.

#### `expand`

A no-op where `expanded` already reads True, since the underlying
action toggles on at least one platform -- calling this twice must
not collapse what the first call opened.

#### `expandable`

Read this before trusting `expanded`. On Windows and macOS it is the
same signal `expand()` and `collapse()` act on. A collapsed branch's
rows are not in the tree at all until something opens it, which is
what `Session.tree_items` walks the tree expanding as it goes.

#### `expanded`

Same caveat as `checked`: read `expandable` first.

#### `find`

The recursive search, where `children` is one level. An empty list is
how it reports no match, rather than raising. The elements it hands
back carry this one's session, so a result can be clicked and
double-clicked like one the session found itself. For anything beyond
role and name -- a state, a description, a predicate --
`Session.elements(within=...)` is the fuller filter.

Unbounded on Linux and Windows, where the toolkit does the searching.
macOS has no tree search to ask, so the walk is this package's own and
carries a budget: 24 levels deep and 20,000 nodes, past which the
answer is what was found so far rather than an error. Deep enough for
any ordinary interface, and reachable by a large Electron document.

#### `focus`

On Windows and macOS a toolkit that will not focus the element says
so with a typed error naming what was attempted, rather than
returning quietly. Either way the grant is the toolkit's to make, so
read `focused` or call `Session.assert_focused` afterwards wherever
the next step depends on it.

#### `focused`

Not every desktop publishes per-widget focus, and one that does not
reports False for everything rather than saying so -- which reads as
a test failure when it is an unsupported desktop. Ask
`Session.focus_tracking_works()` first on a machine you do not know.

#### `is_ancestor_of`

Strictly inside: an element is not its own ancestor. Answered by
walking upwards from `other` rather than descending, since the
question is about one path and descending would visit the whole tree.

How the comparison at each step is made is the platform's: Windows
asks `CompareElements` and macOS asks CoreFoundation, because two
references to one element are distinct objects there as often as not,
while on Linux PyGObject hands back the same wrapper for the same
accessible and `==` is already the right question. The walk is
depth-bounded on Windows and macOS, so a toolkit reporting a cycle
cannot make it spin; on Linux it is not, so a cyclic tree would.

Its use is confirming that a control really belongs to the dialog a
test thinks it scoped the search to.

#### `name`

Always a string on every backend, never None. On Windows and macOS
that is enforced on the way out: an application is free to put a
non-string there, and coercing it is what stops a `TypeError`
surfacing from inside somebody's search instead. On macOS what comes
back is PyObjC's own `str` subclass, so `isinstance(name, str)` holds
but `type(name) is str` does not -- compare and concatenate freely,
and do not test the concrete type. An empty name is the
commonest reason a locator finds nothing -- an icon-only button whose
developer never set one -- and `description` is where the label went
in that case, which makes it the second thing a locator should try.

#### `options`

Menu items first, then list items, on every backend. An empty list is
a truthful answer about a popup nobody has opened yet rather than a
failure, so this is the diagnostic to reach for when `choose` cannot
find an option -- it prints what the control actually offers.

#### `parent`

The direct parent only, and on Windows the parent in UIA's control
view rather than its raw tree. The element handed back carries the
same session this one did, so a walk upwards can still click.

#### `pid`

None where the accessibility bridge publishes none, which is common
enough that a caller must handle it: it is the one field here that
the toolkit is not obliged to answer. Its use is telling elements
of one application apart from another's -- the accessibility bus is
scoped to the login session, not to a display, so on a machine
running two of them the tree carries both.

#### `role`

The spelling is at-spi's on every platform, not the native layer's:
UIA control types and macOS AX roles are both translated on the way
out, which is what makes one `Role.PUSH_BUTTON` locator match on all
three. at-spi2's own disagreements are folded in too -- a push button
reads back the same whether the bridge calls it `"button"` or `"push
button"`.

What an *untranslated* role reads as differs, and only one of the two
is `unknown`: Windows reports `unknown` for a control type outside
the documented range, while macOS spells an unmapped AX role out into
words instead, keeping `unknown` for the case where no role could be
read at all. Either way it is a prompt to run `pyguitest inspect`
rather than to guess.

#### `select`

On Windows and macOS an element that publishes no selection raises
`CapabilityUnsupported` rather than returning quietly: a caller who
asked for a selection and got silence cannot tell that apart from a
selection that happened. `selectable` is the question asked first.

#### `selectable`

Read this before trusting `selected`, for `checkable`'s reason. On
Windows and macOS it is the same signal `select()` acts on, so a
False here is also the reason that call would refuse.

#### `selected`

Same caveat as `checked`: read `selectable` first.

#### `set_text`

Not typing: no key events are sent, so autocomplete, input masks and
per-keystroke validation are never exercised. That is the right call
when the value is the point, and the wrong one when the application's
key handling is what is under test -- `Session.type_text` is that.

On Windows and macOS a control with no way in -- a read-only label, a
document, something that merely looks like a field -- raises
`CapabilityUnsupported`, because "there is no route" is the useful
half of the answer.

#### `text`

None where the element holds no text at all -- and which elements
those are is a platform answer, not a universal one: an at-spi label
reports None while a macOS static text answers with its visible
string, because on a Mac the label's string lives in the one
attribute that holds text. On Windows the read tries UIA's Text
pattern first (a document or a read-only body) and then its Value
pattern (an editable field), which is one property at-spi splits
differently. `value` is the numeric sibling, not this.

#### `value`

A float where the control publishes a value, None where it does not,
on every backend. Linux used to answer dogtail's raw `False` for
anything with no Value interface, which made `value is not None`
true for a push button there and false for one everywhere else; it
is coerced now, so the annotation and the behaviour agree.

One platform difference survives, because it is the toolkit's data
rather than this package's shape: **macOS reports a number for a
tick as well as for a position**, since AX keeps both in the same
attribute. A check box there reads `value == 0.0` alongside
`checked is False`, where Linux and Windows both answer None.
Measured on live trees -- `check box`, `radio button`, `separator`,
`ruler marker` and `dock item` all answered a float on macOS.

So `isinstance(element.value, float)` still does not mean "this is a
slider". Branch on the role: `checked` is the read for a tick and
`text` for an editable field's contents, and `value` is meaningful
only once the role says the control has a position.

#### `visible`

The one property whose meaning genuinely differs by platform, because
no two of these layers answer the same question. at-spi has a
`showing` state. UIA answers `IsOffscreen`, which counts a row
scrolled out of a long list as hidden. macOS publishes no such state
at all, so it is inferred from three things -- the element reports a
rectangle, it is not marked hidden, and its window is in the window
server's on-screen list -- and cannot see a scrolling ancestor having
moved it out of view.

Lenient on Windows and macOS, where a read the toolkit refuses and a
join that cannot decide both answer True: a caller about to act on
the element is better served by the optimistic answer than by a
confident "it is hidden" that is wrong. Linux has no such default and
lets the failed read surface instead. Either way this is a hint, and
the action itself is the better proof.

### Application

A program started by `Session.start_app`, and its lifecycle.

| Member | What it does |
|--------|--------------|
| `is_running()` | Whether the program is still running. |
| `kill()` | Stop the program outright -- SIGKILL on Unix. Not declinable. |
| `pid` | The process id -- what `wait_for_idle` and friends take. |
| `poll()` | The exit status if it has finished, or None. Does not block. |
| `restart(timeout: float = 5.0)` | Stop the program and start it again, same command, same options. |
| `returncode` | The exit status, or None if nothing has reaped the process yet. |
| `send_signal(signal: int)` | Send one signal to the process, by number. |
| `stderr` | The process's stderr, or None unless `start_app` was given a pipe. |
| `stdin` | The process's stdin, or None unless `start_app` was given a pipe. |
| `stdout` | The process's stdout, or None unless `start_app` was given a pipe. |
| `stop(timeout: float = 5.0)` | Stop the program, and do not come back until it is stopped. |
| `terminate()` | Ask the program to quit -- SIGTERM on Unix. Returns immediately. |
| `wait(timeout: float \| None = None)` | Block until it exits, or raise `subprocess.TimeoutExpired`. |

#### `is_running`

A `poll()` underneath, so calling this is also what reaps an exited
process and fills in `returncode`.

This is the launched process's state, which is not always the
application's: a launcher that spawns the real program and exits --
macOS `open -a`, a wrapper script -- reads as *not* running while the
window it opened is still on screen. Where that matters, wait on the
window or an element rather than on this. See `pid` for the same
distinction.

#### `kill`

No chance to save state, and no cleanup. `stop()` already escalates
to this when a polite request goes unanswered within its timeout,
which is usually the call to reach for instead.

On Windows this *is* `terminate()` -- `subprocess` maps both to
`TerminateProcess` -- so a script that tries one and then the other
is doing the same thing twice there.

#### `pid`

The process `start_app` started, which is not always the process that
draws the window. A launcher that spawns the real application and
exits -- macOS `open -a`, a wrapper shell script, a `.desktop`
handler -- leaves this pointing at the launcher, so it will not match
the `Element.pid` or `Window.pid` of the application on screen. Check
with `pyguitest inspect` when a pid-scoped element query comes back
empty for an application that is plainly running.

The string form of `command` is a common cause, and which way it
goes depends on what `/bin/sh` is on the machine. Measured three
ways rather than assumed:

- `/bin/sh` is **bash** (Fedora): bash `exec`s a simple command, no
  shell is left behind, and `start_app("editor file")` reports the
  editor's own pid.
- `/bin/sh` is **dash** (Debian 13, dash 0.5.12-12; Pop!_OS, dash
  0.5.12-6ubuntu5): the shell does *not* exec. `sleep 5` ran as a
  child of a surviving `sh`, so the pid here is the **shell's**, and
  a pid-scoped element query finds nothing. Debian and Ubuntu are
  both in this group, so it is the common case, not the exotic one.

A string the shell cannot finish with an exec at all -- a background
job, a pipeline, a trap -- leaves the shell here on every platform.

Pass the list form, `start_app(["editor", "file"])`, whenever the
pid matters: it runs no shell, so the pid is always the program's.

#### `poll`

Also the call that fills in `returncode`, so this is the one to reach
for in a loop that is waiting without committing to a deadline.

#### `restart`

Returns self, so `app.restart().pid` reads. The new process replaces
`.process`; the old one is stopped first by the rules above.

**The old process's captured output is discarded.** Its pipes -- the
`stdin`/`stdout`/`stderr` a `start_app(..., stdout=PIPE)` gave it -- are
closed here, because nothing can reach them once `.process` is replaced;
left open, each was only reclaimed by the garbage collector, with a
`ResourceWarning` apiece under `-X dev`. Closed rather than drained with
`communicate()`: a program started through the shell can leave a
grandchild holding the pipe, and a drain would then block on it. Read
`app.stdout` before calling this if the old output matters.

#### `returncode`

Read straight off the `Popen`, which means it is None both while the
program is running *and* after it has exited but before anything
asked -- `returncode` is filled in by `poll()`, `wait()`, `stop()` or
`is_running()`, not by the process exiting. So a bare read right
after the program quits still answers None; call `poll()` first, or
read what `stop()` returns.

#### `send_signal`

Unix only in any real sense. On Windows `subprocess` accepts just
`SIGTERM` (which it turns into `TerminateProcess`), `CTRL_C_EVENT`
and `CTRL_BREAK_EVENT`, and raises `ValueError` for anything else --
so a suite that signals a process needs a platform branch rather
than a portable call.

Accepted is not the same as delivered, and the two console events
carry conditions `start_app` does not set up by default. A console
event reaches a process only through a shared console, and
`CTRL_BREAK_EVENT` needs the child in its own process group --
launch it with `creationflags=subprocess.CREATE_NEW_PROCESS_GROUP`
or it will not arrive. `CTRL_C_EVENT` cannot be aimed at one group
at all on Windows, so it reaches every process sharing the console,
this one included. Signalling a process already known to have
exited returns silently on both platforms.

#### `stderr`

None unless the caller passed `stderr=subprocess.PIPE`. Worth piping
when an application fails to appear at all: the reason is usually on
this stream, and `restart()` closes it, so read it first.

#### `stdin`

None is the ordinary answer: `start_app` passes `**kwargs` to
`subprocess.Popen`, so a stream exists only where the caller asked
for one with `stdin=subprocess.PIPE`.

#### `stdout`

None unless the caller passed `stdout=subprocess.PIPE`, and a GUI
program often writes nothing useful there anyway.

`restart()` closes the old process's pipes, so anything still
unread is gone -- but do not reach for `app.stdout.read()` to get
in first: `read()` waits for EOF, which a *running* application
will not give, so the call blocks instead of returning what has
been written. Draining one pipe while the other fills can deadlock
for the same reason the stdlib warns about. Use
`communicate(timeout=...)` on `app.process`, or read incrementally
on a thread, if the output is wanted while the program is alive.

#### `stop`

SIGTERM first, because a GUI program asked to quit politely gets to
save its state; `SIGKILL` only if it has not gone within `timeout`.
That fallback is not theoretical: an editor holding unsaved text
answers SIGTERM by *opening a "Save changes?" dialog* rather than
exiting, so a plain `terminate()` plus an unbounded `wait()` hangs
until someone clicks it (see docs/validation.md, where that cost a
live run).

Idempotent, and never raises: this is what runs while an exception
is already unwinding, and a cleanup path that throws replaces the
real failure with its own. Returns the exit status.

#### `terminate`

Does not wait, and does not escalate: a program that answers the
request with a "Save changes?" dialog simply stays up. `stop()` is
the bounded four-step version, and the one to use in cleanup.

On Windows there are no POSIX signals -- this calls
`TerminateProcess`, which the program cannot decline or handle, so
there is no save-your-state courtesy there and no difference between
this and `kill()`. Both also return silently once `returncode` has
been filled in.

#### `wait`

Unbounded with no `timeout`, which on a GUI program is a real risk
rather than a theoretical one: an editor holding unsaved text answers
a quit request by opening a "Save changes?" dialog and waits for a
human. `stop()` is the bounded version and the one a test wants.

#### `can_capture`

Three routes reach pixels and only one of them is a tool on PATH.
X11Backend captures and encodes a PNG itself given python-xlib and
an X connection, and the Screenshot portal needs nothing installed
at all beyond PyGObject. Reporting "no screen capture" on a session
that has either would send someone off to install a tool they do
not need.

The portal route is the least certain of the three: has_portal is
`_portal()`'s own "a portal service is reachable" heuristic, not
proof that its Screenshot interface is actually implemented behind
it -- confirmed false on a real box where the running backend was
xdg-desktop-portal-gtk, which implements neither Screenshot nor
RemoteDesktop. Narrowing has_portal further would need either a
live D-Bus introspection call at detect() time (a real dependency
this package has deliberately avoided so far) or a per-desktop
allowlist with no live evidence yet for anything but GNOME/Mutter
-- so this can still answer True on a session where the Screenshot
portal will not actually work. What changed instead: a portal call
against an interface nobody implements now raises the typed
BackendUnavailable (see backends/portalrequest.py's call()) rather
than a raw D-Bus exception -- PortalCaptureBackend negotiates
nothing at construction, so a wrong answer here still lets
connect(backend="portalcapture") succeed; the clean failure lands
on the first actual capture() call instead, not surfacing an error
outside this package's own model.

#### `can_inject_input`

has_portal does not count on its own: nothing in this package can
actually drive a portal transport yet, only external CLI tools and
in-process uinput. Counting it would report "injectable" on a
machine where nothing can actually inject, which suppresses the
"install an input tool" hint exactly where it is needed most.

Windows answers from its own field, before any of those are read:
every mechanism named below is a Linux one, so without this branch a
Windows session injected input perfectly well and reported False
here -- and every hint gated on that then sent the reader off to
install ydotool.

macOS answers from its own field too, and from the *right* one: what
`CGEventPost` needs is the PostEvent grant, not Accessibility, even
though System Settings files both under one pane. Reading `has_ax`
here would refuse input on a machine that had granted exactly what
input requires.

#### `can_use_atspi`

Needs all three pieces: the libatspi service and the PyGObject
binding, both from the distro, plus dogtail, the one part pip
actually supplies (see the 'atspi' extra). The distro halves alone
are common on a fresh box where nobody has run `pip install
pyguitest[atspi]` yet, and reporting that as support would silence
the hint that says so -- see hints.py -- while AtspiBackend still
fails to construct.

False on Windows by definition rather than by absence: AT-SPI is a
Linux accessibility bus and there is none there, so nothing is
missing. The Windows element tree is UI Automation, and
`has_comtypes` is what says whether it can be opened -- deliberately
not folded in here, because this property's name would then mean two
different things on two platforms, which is the trap the rest of the
Windows work exists to avoid.

#### `can_use_clipboard`

On Linux and the BSDs there is one route and it is a CLI tool:
nothing in this package speaks a clipboard protocol directly, so
clipboard_tools is the whole answer -- see tools.CLIPBOARD_TOOLS on
why Mutter is the one desktop where that can come back empty.

Windows is the exception, and answers before that: `Win32Backend`
opens the clipboard itself through user32 and kernel32, so no tool is
involved and an empty `clipboard_tools` says nothing. Confirmed on
Windows 11, where this was False beside a backend declaring
CLIPBOARD -- the same miss as `can_capture` above.

macOS answers from `clipboard_tools` as well, and reaches the
clipboard through a tool rather than through a binding: `pbcopy` and
`pbpaste` ship with the OS, so a Mac answers True unless they have
been kept off PATH. ADR 004 left the choice between this and an
`NSPasteboard` element in the `macos` backend open and named this one
the obvious way in -- and it needs no branch here at all, which is why
the last paragraph of this docstring is history rather than code.
`MacosBackend` declares no CLIPBOARD of its own, and the pasteboard is
a single selection, so `primary=True` is refused rather than aliased
(see clipboard.py).

What this deliberately does **not** do is answer from
`has_pyobjc_quartz`, the binding that pulls in Cocoa and so would
carry `NSPasteboard` if anything used it. That would report a
capability one backend too early -- the same read `can_capture` above
exists to avoid in the other direction, and the miss this property
was fixed for in 0.14.0.

#### `input_transport`

`preferred_input` answers the narrower question and is None on a
machine served by in-process uinput -- which made `summary()`
print "input none available" on a session whose own `mechanisms`
line, two rows below it, correctly said `uinput`.

The order mirrors `backends._input_factory`, the thing that
actually chooses: keymap-safe tools first, then in-process uinput,
then keymap-unsafe tools, which uinput outranks because it costs no
process per event and is no less safe. libei comes last and says
it is opt-in -- automatic composition never selects it, so naming
it plainly would describe a session nobody gets without asking.

These are labels for a person reading `summary()`, not names to
pass to `connect(backend=...)`.

Windows is answered first and on its own: SendInput is in-process,
needs no tool and opens no device, so there is nothing on that
platform for the ranking below to choose between.

#### `preferred_input`

Deliberately narrow: it ranks `input_tools`, and a session that
injects input perfectly well through no tool at all answers None
here. `input_transport` is the wider question -- what will
actually carry the events -- and is what `summary()` reports.

## Capabilities

The full set, with the tier each sits in and the backends providing
it. Tiers come from the audit and are ordered by cost: tier 6 is what
Wayland prevents by design, which is why a Wayland session cannot 
serve them. On X11, XWayland, Windows or macOS they are ordinary 
calls, and the X11-only mark appears only where no other backend 
provides the capability at all -- which today is nowhere.
